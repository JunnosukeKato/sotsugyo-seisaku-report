# 卒業制作報告書 作成ツール：引き継ぎ手順

このツールを担当する人が替わるときと、担当の人が年に何回か行う作業のための手順書です。
プログラムに詳しくない人でも、上から順に読めば分かるように書いています。

---

## 1. しくみ（全体の形）

| 部分 | 何をするか | 置き場所 |
|---|---|---|
| 学生用ツール | 学生が報告書を書き、PDF を書き出す | GitHub Pages（GitHub のリポジトリから自動で公開） |
| 管理ページ | 先生が年度の設定（題目・コース・指導教員・締切・ひな形・お知らせ・書き間違えやすい語）を編集・公開する | Google Apps Script「卒業制作報告書_管理」（管理用スプレッドシートに付属） |
| 管理用スプレッドシート | 年度の設定・変更履歴・管理者と先生の一覧 | Google ドライブ「卒業制作報告書_管理」 |
| 配信の窓口 | 学生用ツールに、公開中の年度の設定を渡す（誰でも読める） | Google Apps Script「卒業制作報告書_配信」 |
| ドライブ保存のログイン | 学生が大学のアカウントでログインし、自分の Google ドライブに原稿を保存する | Google Cloud のプロジェクト「sotsugyo-seisaku-report」（組織 bunka-wu.ac.jp、対象は「内部」） |

**学生の原稿と写真は、学生本人のブラウザと、学生本人の Google ドライブ（「卒業制作報告書」フォルダ）にだけ保存されます。**
学科のスプレッドシートやサーバーには集まりません。

管理ページと配信の窓口は、どちらも**「デプロイした人」（プログラムを Apps Script に送って公開した人）の権限で動きます**（`gas/*/appsscript.json` の `executeAs: USER_DEPLOYING`）。
管理用スプレッドシートを読み書きするのは「デプロイした人」で、管理ページを使う人がそれぞれスプレッドシートの共有を受けている必要はありません。
管理ページを使えるかどうかは、スプレッドシートの「管理者」シートに載っているかで決まります。

## 3. 毎年の作業（管理ページ）

1. 管理ページを開き、「新年度を作成」で、前年度の設定をコピーして新年度を作る（「準備中」になり、学生には見えない）
2. 共通の題目・コース・指導教員・締切を直す。右の見本で表紙と抄録を確かめる
3. 必要なら、コースのカードで「下書きのひな形」と「このコースの学生へのお知らせ」を直す
4. 「この年度を学生に公開」を押す（前の年度は「終了」になる）
5. 学生用ツールの URL を学生に知らせる

- 原稿は、**書き始めた年度の設定で開きます**。新年度を公開しても、前年度の学生（留年など）の表紙は前年度のままです。新年度で書き直したい学生は、右の欄の「バックアップ」→「最初から作り直す」で新年度の原稿にできます（前の原稿は「自動の控え」に残ります）。
- 公開中の年度を保存すると、1分以内に学生のツールに反映されます。
- 変更履歴から、過去の内容に戻せます。
- ほかの人（先生など）が保存したあとに、古い画面のまま保存・公開しようとすると、保存・公開されずに知らせが出ます（先生の画面の保存も同じです）。ページを読み込み直してから、もう一度変更してください。
- コースの「お知らせ」は、**インターネット上の誰でも読めます**（配信の窓口は誰でも読めるため）。個人の情報（連絡先など）は書かないでください。
- 下書きのひな形・お知らせ・書き間違えやすい語は、形が崩れていたり長すぎたりすると、保存されずに知らせが出ます（見出しの名前は100字、説明は300字、お知らせは1000字、語の一覧は300語まで）。

### 管理者と先生の登録

- 管理ページの「先生の登録」で登録します。メーリングリストの宛先をそのまま貼り付けて、まとめて登録できます（学生のアドレスと、大学のアドレスでないものは登録しません）。
- **管理者**：すべての設定の変更と公開、先生の登録ができる
- **先生**：どのコースの「下書きのひな形」「お知らせ」と、「書き間違えやすい語」を編集・保存できる
- 登録は、スプレッドシートの「管理者」シート（メールアドレス・メモ・役割）に入ります。役割は「管理者」か「先生」と書きます（空欄は管理者。それ以外の書き方の行は使えません）。
- 登録・役割の変更・登録を外したこと（だれが、いつ、だれを）は、スプレッドシートの「変更履歴」シートに残ります（年度の欄が空の行）。
- 管理者が1人もいなくなる変更（最後の管理者を先生にする・外す）はできません。自分を先生にしたり外したりすることもできません。
- 「管理者」シートを手で直すときは、役割の書き間違いやシート名の変更に気をつけてください。管理者が0人になると、管理ページではだれも登録を直せなくなります（そのときは 6 の「管理者がいなくなった」を参照）。

## 4. 担当が替わるときにすること

前の担当者と新しい担当者が一緒に行うと確実です。

1. **管理ページ**：新しい担当者を「管理者」として登録する
2. **管理用スプレッドシート**：新しい担当者に「編集者」で共有する（管理ページのプログラムはスプレッドシートに付属しているので、一緒に移ります）
   - 共有の設定は「一般アクセス：制限付き」にし、編集者は管理者2人程度だけにする。スプレッドシートの編集者は、「管理者」シートに自分を書けば管理者になれ、付属のプログラムも書き換えられるため
   - 共有ドライブに置くなら、学科全体の共有ドライブではなく、メンバーを絞った**このツール専用の共有ドライブ**にする（共有ドライブのメンバーは、全員がスプレッドシートの編集者になるため）
3. **配信の窓口**（Apps Script「卒業制作報告書_配信」。スプレッドシートに付属しない、単独のプロジェクト）：新しい担当者に共有し、持ち主を新しい担当者に移す（または 2 のこのツール専用の共有ドライブへ移す）
4. **配り直しと承認**：管理ページと配信の窓口は「デプロイした人」の権限で動きます（1 を参照）。前の担当者のアカウントが使えなくなっても動くよう、新しい担当者が次を行う
   1. 自分のパソコンで `npm run deploy:gas` を実行して配り直す（5 を参照）
   2. Apps Script のエディタで、管理ページは `setup`、配信の窓口は `authorize` を1回実行して、表示される画面で承認する
   - 配り直すだけで「デプロイした人」が新しい担当者に替わるか、承認がいつ要るかは、本物で確かめる（Apps Script の「デプロイを管理」で、実行するユーザーとデプロイした人を確かめる。替わったあと、管理ページと学生用ツールが年度の設定を読めるかも確かめる）
   - `npm run deploy:gas` は、今あるデプロイを新しい版に更新するので、管理ページと配信の窓口の **URL は変わりません**。Apps Script の画面で「新しいデプロイ」を作ったときだけ URL が変わります。そのときは `gas/deployments.json`（配信の窓口なら `.env` の `VITE_CONFIG_API_URL` も）を直して、学生用ツールを公開し直す（5 を参照）
5. **Google Cloud**：プロジェクト「sotsugyo-seisaku-report」の「IAM」で、新しい担当者を「オーナー」に加える。Google Cloud の画面に入るには、2段階認証の設定が必要
6. **GitHub**：リポジトリを新しい担当者（または学科の組織）に移す（Settings → Transfer）。移すと学生用ツールの URL が変わるので、学生への案内と、Google Cloud のクライアントの「承認済みの JavaScript 生成元」を新しい URL に合わせる
   - 管理ページの「使い方（教員用の手引き）」のリンク（`src/admin/AdminApp.tsx` の `TEACHER_GUIDE_URL`）も新しい URL に直す。手引き（`docs/手引き_*.html` と `scripts/make-guides.mjs` の URL）も直して `node scripts/make-guides.mjs` で作り直す
   - リポジトリに送れる（push できる）人は、**全学生に任意のプログラムを配れます**（main に送ると、自動で学生用ツールとして公開されるため）。送れる人は担当者だけにし、その人の GitHub のアカウントには必ず2段階認証を設定する
   - main ブランチを保護する（Settings → Branches（または Rules）で、main を消したり履歴を書き換えたり（force push）できないようにする。できれば、テストが通らないと main に入れられないようにする）
7. **開発計画書**（`卒業制作報告書/開発計画書.md`）：前の担当者のパソコンにだけあるので、新しい担当者に渡す。公開のリポジトリには入れず、2 のこのツール専用の共有ドライブなど、関係者だけが見られる場所に置く
8. **反映の道具**：新しい担当者のパソコンに、5 の準備をする

## 5. プログラムを直して反映する

### 準備（はじめて1回）

1. Node.js（LTS 版）と Git を入れる
2. GitHub からリポジトリを取ってくる：`git clone https://github.com/JunnosukeKato/sotsugyo-seisaku-report.git`
3. フォルダの中で `npm install`
4. Apps Script に送るための道具にログインする：`npx clasp login`（大学のアカウントを選ぶ。https://script.google.com/home/usersettings で「Google Apps Script API」をオンにしておく）

### 直して確かめる

```
npm run dev       # 開発用のサーバー（http://localhost:5173）。?nodrive を付けるとログインなしで試せる（開発中だけ）
npm test          # 単体テスト
npm run e2e       # 画面の通しテスト（Edge を自動で操作。開発用のサーバーを動かしておく）
node scripts/e2e/admin.mjs   # 管理ページの通しテスト
```

### 反映する

- **学生用ツール**：`main` に送る（`git push`）と、GitHub Actions がテストして自動で公開する（数分）
- **管理ページと配信の窓口**：`npm test` が通ることを確かめ、変更をコミットして GitHub に送って（`git push`）から `npm run deploy:gas`（URL は変わらない）
  - コミットしていない変更があるとき、main ブランチでないとき、main が GitHub の main と違うとき（送り忘れ・取り込み忘れ）は、理由を出して止まります。動いているプログラムと、GitHub で公開しているソースコードを同じにするためです

### 気をつけること

- 提出の締切の前（12月〜1月）は、組版の部品（`@vivliostyle/core`）を更新しない。ページの割り方が変わることがある
- このツールは AGPL-3.0 で公開している。直したら、GitHub にも必ず送る（動いているプログラムと公開しているソースコードを同じにする）
- 公開のリポジトリに、学生や教職員の個人のメールアドレス・個人のデータを入れない

## 6. 困ったとき

| こんなとき | すること |
|---|---|
| 学生がログインできない | ブラウザのポップアップを許可する。LINE や Classroom アプリの中で開いていたら、Safari や Chrome で開き直す。大学のアカウントを選んでいるか確かめる |
| 全員がログインできない（Google の障害・大学の設定変更） | 管理ページ →「詳細設定（手順書の改訂・Google の障害のとき）」→「学生のドライブ保存」を「止める」にして保存する（1分ほどで反映。学生はページを読み込み直すと、ログインせずに書ける。原稿はその端末にだけ保存）。あわせて情報システムの担当に相談する。`drive-test.html` で、どの段階で止められているかが分かる。直ったら「必須」に戻して保存する。学生への知らせ方は、次の行を参照 |
| 障害などを、学生全員に知らせたい | 管理ページには、全員向けのお知らせの欄はありません（コースの「お知らせ」は、そのコースの学生がツールを開けたときにしか見えません）。Classroom・メールなど、学科のふだんの連絡手段で知らせる。「ページを読み込み直す」「ログインせずに書けるあいだは、同じ端末で続ける」「直ったら知らせる」などを書く |
| 管理ページに、ある年度が出てこない | スプレッドシートの「年度設定」シートの、その年度の行が書き損じで読めない（手で直したときなど）。「変更履歴」シートから、その年度の前の「設定（JSON）」を写し、更新日時の欄に日時を入れる。公開中の年度の行が読めないあいだ、学生のツールは前に読み込んだ設定（なければツールに入っている初期値）で動く |
| 管理者がいなくなった（「管理者」シートの役割を書き間違えた・シート名を変えた） | 管理ページではだれも直せないので、スプレッドシートの編集者が「管理者」シートを直す（シート名は「管理者」、役割は「管理者」か「先生」）。または、管理ページをデプロイした人が Apps Script のエディタで `setup` を実行する（実行した人が管理者に登録される） |
| 管理ページの変更が学生に出ない | 公開中の年度を保存したか確かめる。反映まで1分かかる。学生はページを読み込み直す |
| 間違えて設定を変えた | 管理ページの「変更履歴」から、前の内容を読み込んで保存する |
| 学生が原稿をなくした | 右の欄の「バックアップ」→「自動の控え」、または学生の Google ドライブの「卒業制作報告書」フォルダの「原稿.json」（右クリック →「版を管理」で前の版）を確かめる |
| 学生が「別のタブで開いています」と言う | 同じパソコンの別のタブ（窓）でツールを開いている。もう一方を閉じてから「こちらで続ける」を押してもらう（2か所で書いて内容が消えるのを防ぐため） |
| 学生が「エラーが消せないので先生に見せられない」と言う | エラーが残っていても、「PDFを書き出す」→「下書きの PDF を書き出す」で、どのページにも「下書き」の透かしが入った PDF を出せる（提出には使えない） |
| 指摘が正しくない（引用の中の言葉など） | 「文末の。」など手順書のルールでない補助の指摘は、学生が「このままにする（確認済み）」で外せる（右の欄の「確認済み」から「戻す」で戻せる）。手順書のルールの指摘は外せない |
| 共用のパソコンで書き終えた | 学生に、保存のようす（右の欄）→「この端末から原稿を消す」を押してもらう。Google からのログアウトも忘れずに |
